# Solution Request #336 - MBRDI
**Date:** 2026-09-30  |  **Status:** Pending Update  |  **Complexity:** Not Set

## Brief
MBRDI-Workday integration which changes the existing workflow

## Problem Description
PFB the requirement in detail. 

Our observations are below, grouped by area, followed by what we need to put the action plan together.

Change request: new fields in the employee-data file
• The current PROD configuration has 34 columns.
• The 3 newly requested fields can be accommodated by mapping them onto our 3 reserved columns:
– EMPLOYEE_ID_PAY
– GRADE_PROFILE
– GRADE_PROFILE_MAP1
• This uses up our pool of configurable fields. Once these are added, we will not be able to accept any further requests for new fields on this file.
• Question for the MBRDI Team: what does EMPLOYEE_ID_PAY represent, and will the existing employee_id values stay the same after the move to Workday? MBRDI users log in with their employee ID, so any change to the existing IDs would break login for the affected users.
 
Answer -  EMPLOYEE_ID_PAY represents the MBRDI employee ID. Existing Employee values will be same 

 
Integration model: file-based SFTP continues
• The SOW / business requirement refers to "...end-to-end connectivity between Vantage Circle and Workday...".
• My understanding is that the MBRDI Team is migrating its HRMS to Workday but will keep the existing file-based integration via SFTP, not an API integration. Please confirm this is correct.
• If so, no changes to the SFTP location or setup are required.
• The MBRDI Team must follow the newly configured CSV column sequence exactly before dropping files at our SFTP location for processing.

Answer - existing file-based integration via SFTP and there will be no change to existing file transfer set up

System re-configuration: workflow integrity
• The SOW mentions "system re-configuration" for this migration and change request. The Workflow team needs to be involved to verify that the existing workflow still works correctly.
• Risk: for MBRDI, the budget approval flow finds the approver through a wallet account named after the employee's department. If department names change in Workday, no approver will be found, and nothing fails visibly at that step. We need the MBRDI Team to confirm whether department names are changing.
Answer - there may be some functional changes in Workday .

New data mapping for grade_group (Legacy Level / Employee Level / WD Management Level)
• The MBRDI Team will be revising the values for this field, and the workflow depends on it.
• Risk: the workflow's use of grade_group is set up in platform configuration, not in code, and grade groups are matched by name. Renamed values will not match the existing setup unless that configuration is updated or the data is migrated.
• The Workflow team needs to assess the impact: can the new values be ingested as-is, or is a data migration and clean-up needed first?
• Reports: showing the new values on historical records is not feasible. Only records generated from now on will carry the new values.

Answer - The data mapping should be done for the exiting levels to new grades.

The Solution team needs to assess the impact: can the new values be ingested as-is, or is a data migration and clean-up needed first?


Next steps:
Based on the above, we need a detailed, actionable plan that includes the dependencies on each cross-functional team. 

Solution team: verify workflow integrity for the re-configuration, including the department-based approver lookup; review & call out edge cases that might arrive
