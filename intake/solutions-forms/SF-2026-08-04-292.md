## Solution Given
The proposed solution:

A single consolidated reminder email, sent twice a month on the 14th and the 28th, morning IST, covering every points  expiring in the next 90 days:

One email per employee per run, no matter how many points  are expiring.
A table of expiring points, points value and expiry date, sorted earliest first.
Points sharing the same expiry date are summed into one row, and we show a maximum of three rows.
Total expiring and total available balance shown as two clearly separate figures.
Once the employee redeems, the points drops out of the next run automatically. No opt-out flag, no admin step.


Twice a month across 90 days gives roughly six touchpoints per points expiry, which matches what the client asked for. They had originally proposed six separately triggered emails at 90 / 60 / 30 / 14 / 7 / 1 days. We moved to a digest deliberately, with multiple points per employee, six date-triggered emails would multiply into an unpredictable number of emails per person per month, whereas a fixed twice-monthly schedule is bounded, predictable and much simpler to support.

This needs development and it is not a configuration change

1. The table is the real change. The current expiry email is built to show a single points figure and a single expiry date. It needs a list of points passed into the template. An existing idle-points reminder already renders a table and is probably the cheaper base to start from.
2. The selection query has to change to a date range. Existing per-company expiry reminders match the expiry date exactly. On a 14th/28th schedule an exact match would only catch points expiring exactly 90 days out, which would miss almost the whole population.
3. A new scheduler entry is needed, gated to company 1373, and it must run after the daily points-invalidation job so we never list a points that lapsed that morning.
